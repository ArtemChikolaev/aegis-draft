## 1. Краткое резюме (TL;DR)

Roguelite про **драфт «команды всех времён»**. Игроку выдаются «паки», из каждого он забирает игрока в состав по ролям, раздаёт героев и максимизирует `Team OVR = Base + Hero Synergy + Chemistry`. Цель — собрать сильнейшую пятёрку и «пройти International всухую».

**Ключевой факт про оригинал:** 322-0 — это **статичный SPA** (Vite), грузящий 7 предрассчитанных JSON из `/data/*.json`. Рантайм-бэкенда нет. Вся сложность (и все баги — «странный парсинг») сидят в **офлайн-пайплайне** генерации этих данных.

**Наша ставка:** главная инженерная ценность — прозрачный, версионированный **data-пайплайн на Go**; фронт на **TS/React**; данные отдаём **статикой** (static-first), сервер добавляем позже под мета-фичи.

## 2. Разбор оригинала (322-0)

Название — отсылка к мему «322» (договорняк) и к идее «flawless» (безупречный проход турнира).

### 2.1. Настройки старта (оригинал)
| Параметр | Опции оригинала |
|---|---|
| Режим | `322-0 Classic`, `Esports Manager (beta)` |
| Game Mode | `Classic` (5 игроков + 5 героев в паке) |
| Format | `Valve Legacy`, `Standard (~2 года)` |
| Difficulty | `Hard` (0), `Easy` (1), `Smurfing` (2 реролла) |
| Scoring | `Event Rating`, `Peak Rating` (soon) |
| Hero Allocation | `Automatic`, `Manual` |

### 2.2. Игровой цикл (Classic)
1. Показывается **пак** = одна команда на одном турнире → 5 игроков (роли + рейтинги) + 5 сигнатурных героев.
2. Забираешь **одного игрока** → он встаёт в слот своей роли на пентагоне.
3. Появляется следующий пак. Повтор, пока не заполнены 5 ролей.
4. Параллельно копятся герои → распределяются по игрокам (авто/вручную).
5. **Reroll** заменяет пак (лимит = сложность).
6. Итог: `Team OVR` = `Base + Hero Synergy + Chemistry` + радар-пентагон.

### 2.3. Формула
```
Team OVR = Base + Hero Synergy + Chemistry
```
- **Base** — средний event-OVR пятёрки.
- **Hero Synergy** — бонус за оптимальное назначение героев (games-driven: по числу pro career-игр player×hero; winrate — вторичный tie-break).
- **Chemistry** — бонус за сыгранность выбранных игроков вместе.

## 3. Модель данных оригинала (референс-схема)

7 файлов `GET /data/*.json` (схемы сняты с боевого сайта).

### 3.1. `events.json` (массив, 44)
```json
{ "id": "ti2011", "name": "The International 2011", "short": "TI1",
  "type": "ti", "year": 2011, "patch": "6.74", "formats": ["valve_legacy"] }
```

### 3.2. `packs.json` (массив, 703) — (команда × турнир)
```json
{ "id": "ti2011-9149636", "eventId": "ti2011", "teamId": 9149636,
  "teamName": "EHOME", "tag": "EHOME", "logoId": "...", "placement": 2,
  "players": [ { "steamId": 89399750, "nickname": "QQQ", "role": "support",
    "ovr": 83, "impact": 79, "economy": 78, "reliability": 78, "games": 14 } ],
  "signatureHeroes": [31, 17, 69, 1, 38, 63, 13, 16, 53, 34] }
```
`role ∈ {safelane, mid, offlane, support}` (support ×2). `ovr/impact/economy/reliability` — производные (0–100) = **IMP/ECO/REL** в UI.

### 3.3. `heroes.json` (массив, 127)
```json
{ "id": 102, "name": "Abaddon", "picture": "abaddon" }
```

### 3.4. `playerHeroStats.json` (объект, 594) — player→hero→{games,winrate}
```json
{ "1185644": { "1": { "games": 14, "winrate": 0.6429 } } }
```

### 3.5. `teammates.json` (объект, 589) — player→[account_id тиммейтов]
### 3.6. `squadSynergy.json` (массив, 3865) — `{ "ids":[a,b], "games":1884, "winrate":0.5642 }`
### 3.7. `eventHeroStats.json` (объект, 44) — event→player→hero→{games,winrate}

### 3.8. ⚠️ Дефекты оригинала («странный парсинг») — что чиним
1. **Рассинхрон id.** В `packs`/`eventHeroStats` — `steamId`, в `playerHeroStats`/`teammates`/`squadSynergy` — иные account_id. Часть связей не матчится. → **Единый канонический `account_id` во всех сущностях.**
2. **Мелкие выборки** (`games:1–2`, wr 0/1) шумят. → **Байесовское сглаживание** рейтингов.
3. **Непрозрачный OVR.** → Явно **специфицируем и версионируем** модель (§5).

## 4. Источники данных

Ядро статистики — **OpenDota** (по `hero_id` = Valve constants и account_id видно, что это не Dotabuff). Метаданные турниров — **Liquipedia**.

| Данные | Источник | Статус / примечание |
|---|---|---|
| Турниры, даты, патчи, команды, ростеры, placement, лого | **Liquipedia API** | ⛔ Нужен одобренный API access. На 2026-07-11 Basic временно недоступен; free-доступ возможен по заявке для подходящих open-source/non-commercial проектов. Реализация следует выданной OpenAPI-спеке/лимиту; обязательны выданная auth scheme, контактный User-Agent, кэш и атрибуция CC-BY-SA. Wiki/MediaWiki scraping как обход не используем. |
| Pro-матчи, пики/бэки, результаты | **OpenDota API** | ✅ Free Tier без ключа: текущая конфигурация сервиса — 60 req/min и 3000 req/day. Premium key отдельный от Steam API key, требует OpenDota login/billing и даёт более высокий лимит. |
| Player×hero игры/винрейты | **OpenDota** (`/players/{id}/heroes`, агрегация матчей) | Основа Hero Synergy / Peak. |
| Сыгранность пар, тиммейты (Chemistry) | **OpenDota** (`/players/{id}/peers` + агрегация pro-матчей) | `/peers` даёт пожизненные совместные игры с каждым тиммейтом — прямой источник Chemistry. |
| Картинки героев/лого | Valve CDN / Liquipedia | Кэшируем локально. |

### 4.1. Про Dotabuff / Datdota (ответ на вопрос «можно ли парсить и не проще ли брать всё с Datdota?»)
- **Liquipedia — да**, только через одобренный официальный API access (см. выше). До одобрения источник заблокирован, а не заменяется скрейпингом.
- **Dotabuff — технически можно, но не рекомендуется.** У Dotabuff **нет публичного API** — только скрейпинг HTML, что: (а) противоречит их ToS и защищено Cloudflare; (б) хрупко (вёрстка меняется); (в) **избыточно** — всё, что показывает Dotabuff, доступно через OpenDota/STRATZ API легально.
- **Datdota — не источник для нас (решение 2026-07-12).** 322-0 внизу пишет «stats from Datdota», но это не пример для копирования: **Datdota и 322-0 — один автор (Noxville)**, он ходит в собственную БД, а не скрейпит. У Datdota **нет публичного API**, данные проприетарны, скрейп против ToS — тот же класс, что Dotabuff. Воспроизвести путь 322-0 мы легально не можем, и это не нужно: всё, что нам не хватает (пожизненные co-games, career/event player×hero, tier-1 фильтр по лигам), **OpenDota отдаёт напрямую** (`/players/{id}/peers`, `/players/{id}/heroes`, `/proMatches`+`/matches/{id}`+`/leagues.tier`). Разрыв с 322-0 был не в источнике, а в объёме собранного (один турнир вместо мульти-эвентного окна).
- **Вывод:** **OpenDota (+ Liquipedia для метаданных) полностью покрывают потребность**; Dotabuff/Datdota — не основа и не дополнение.

> Принцип: сырьё тянем один раз в raw-слой, детерминированно пересчитываем в игровые JSON. Пользователь в рантайме к внешним API не ходит.

## 5. Игровые механики (что специфицируем сами)

### 5.1. Роли — как в 322-0, без деления саппортов
Деление на semi/hard support **отклонено**: по игре часто 5-ка уходит фармить, а 4-ка качает варды — приоритет фарма ненадёжно отражает позицию, будет много ошибок классификации. Оставляем схему оригинала:

| Слот | Роль | `role` |
|---|---|---|
| 1 | Safelane / Carry | `safelane` |
| 2 | Mid | `mid` |
| 3 | Offlane | `offlane` |
| 4 | Support | `support` |
| 5 | Support | `support` |

`role ∈ {safelane, mid, offlane, support}`, где `support` встречается дважды. Два саппорт-слота **взаимозаменяемы** (любой саппорт ложится в любой из двух).
Пак обязан содержать валидную пятёрку ролей, но может включать substitutes сверх пяти; схема и UI не должны отбрасывать их молча.
OpenDota `lane_role` не используется для искусственного деления support на position 4/5: оба игрока остаются просто `support`, как в 322-0. Для M2 player×hero/chemistry роли не требуются вообще.

### 5.2. Рейтинг игрока (Base / OVR)
Из матчей игрока агрегируем и нормируем в 0–100 **с весами по роли**:
- **IMP (Impact)** — KDA, участие в убийствах, урон по героям, teamfight-вклад.
- **ECO (Economy)** — GPM/XPM, net worth к таймингам, ластхиты (с поправкой на роль).
- **REL (Reliability)** — смерти, выживаемость, консистентность по картам.
- **OVR** — взвешенная свёртка (веса зависят от роли: кэрри ≠ support; деления support на 4/5 нет).
- Версионируется: `ratingModelVersion` в артефакте данных.

#### Rating model `v1.0.0`

Первая воспроизводимая модель использует только сигналы, реально доступные в текущих OpenDota match details:

| Компонент | Метрики | Веса |
|---|---|---:|
| IMP | `(K+A)/max(1,D)` · kill participation · hero damage/min | 35% · 30% · 35% |
| ECO | GPM · XPM · last hits/min | 45% · 35% · 20% |
| REL | deaths/10 min (меньше лучше) · консистентность KDA/GPM/damage между картами | 65% · 35% |

Каждая метрика сравнивается **внутри своей роли**, а не между carry и support. Сначала наблюдение сглаживается к среднему ролевой когорты: `x' = (n·x + k·μ_role)/(n+k)`, затем percentile-score дополнительно сжимается к нейтральным 50: `score = 50 + (percentile-50)·n/(n+k)`. В `v1.0.0` `k=8`; для consistency эффективная выборка равна `max(0, games-1)`. Так одна выдающаяся карта не превращается в рейтинг 100.

| Роль | IMP | ECO | REL |
|---|---:|---:|---:|
| Safelane | 40% | 45% | 15% |
| Mid | 45% | 40% | 15% |
| Offlane | 45% | 25% | 30% |
| Support ×2 | 45% | 15% | 40% |

Оба support-слота используют одну формулу. Net-worth timings и полноценный teamfight contribution не подменяются догадками: они могут войти в следующую версию только после появления надёжных данных. Назначение роли приходит из normalize/roster слоя; rating-модель сама роль не угадывает.

### 5.3. Режимы драфта: Team Packs vs Mixed Draft 🔄
Новая ось настройки — **Draft Style**:

- **Team Packs (Classic).** Пак = реальный ростер **одной команды** на турнире (5 игроков всех ролей); берёшь одного игрока (как в оригинале). Скоринг — event/peak рейтинг игрока.

- **Mixed Draft.** 🔄 Пак = **5 игроков из РАЗНЫХ команд**, по одному на роль (напр. `Ame` (carry) · `bzm` (mid) · `33` (off) · `Boxi` (sup) · `Kataomi'` (sup) — каждый из своей команды). То есть внутри одного ролла — не ростер команды, а синтетический «микс-лайнап» из звёзд разных команд. Берёшь **одного** игрока в свой состав, остальные — контекст/превью; реролл даёт новый микс-лайнап.
  - **Порядок ролей — свободный:** из каждого пака можно взять кандидата любой ещё незаполненной роли. После пика carry/mid/offlane эта роль блокируется; два support-слота взаимозаменяемы и закрываются последовательно. Решение зафиксировано по UX-аудиту TREF7.
  - **Скоринг игроков в Mixed — по успеху команды за окно** (не по форме на конкретном событии): рейтинг игрока = функция от результатов его команды(-д) за выбранный период (**1 / 2 / 5 лет**, та же ось Format, что и в классике). Успех = placements/призовые/винрейт на тир-1 ивентах за окно, с поправкой на индивидуальную форму. Так «Ame из чемпионского состава» весит больше, чем тот же игрок из команды-аутсайдера. Детали формулы — §5.4.3.
  - **Chemistry обычно ниже** (звёзды из разных команд не сыграны вместе) — осознанный трейд-офф «сильные индивидуально vs сыгранные». Источник реиграбельности.
  - **Герои:** каждый игрок-кандидат приносит свои сигнатурные герои; при пике добавляем их в общий пул.

> Оси независимы: `Draft Style × Format × Difficulty × Scoring × Allocation`.
> Как валидировать очки игроков в Mixed — см. §5.4.3 (team-success rating).

### 5.4. Scoring
#### 5.4.1. Event Rating
Форма игрока **на событии пака**. Один и тот же игрок на разных турнирах = разный счёт (это фича). Используется в Team Packs.
- **Per-event, а не career:** Base игрока = как он **и его команда суммарно отыграли конкретный турнир**. Один и тот же игрок может быть 60 на одном ивенте и 90 на другом. Это и есть основной baseline (career/peak — отдельная ось Scoring, §5.4.2).
- **Scope = только tier-1 сцена** (подтверждённое решение 2026-07-12). Правило tier-1 = **exclude-based + порог матчей**, потому что OpenDota-тир ненадёжен: `premium` — всего ~214 лиг и не покрывает реальные топ-турниры (EWC 2026, DreamLeague S19/23/24, OGA PIT, EPICENTER помечены `professional`). Поэтому:
  - **tier-1 = `premium` ∪ (`professional` − шум)**, где шум — квалы/дивизионы/регионалки/минорки/бегиннеры и т.п. (паттерны в `pipeline/internal/tier1`);
  - **порог**: события с `< N` матчей в окне отбрасываются (`--min-event-matches`, дефолт 8) — гасит мелкий остаток шума и недосбор;
  - `valve_legacy` = все The International (по имени) + курируемый набор Valve/DPC Major id (классические Kiev/Boston/Shanghai в OpenDota — `professional`, по тиру не выделить).
  - Не-tier-1 матчи в рейтинг/синергию/химию не входят.
- **Event Rating влияет ТОЛЬКО на Base, не на пул Hero Synergy** (`ratingModelVersion v1.5.1`, 2026-07-15). Пул player×hero для **назначения и скора** — **pro career all-time** (`careerPlayerHeroStats`: tier-1 pro match details, **без pub**); `playerHeroStats` — то же, но только в rolling-окне формата (recent form). OpenDota `/players/{id}/heroes` **не используем** (pub+pro давали absurd picks и завышенные счётчики вроде 1400 игр на Timber). Event/point-in-time сверху НЕ накладывается (Real Tournament, §5.9.1). Логика: `heroStatsForAssignment` + `heroStatsForDisplay` → pro career.

#### 5.4.2. Peak Rating — скользящее окно 🔄
Career-best форма игрока, **не привязанная к турниру пака**. Определение:
- Peak = **максимум по карьере** рейтинга игрока в роли драфта, посчитанного по **скользящему окну 3–6 месяцев** (а не по лучшему одиночному турниру).
- **Почему окно, а не турнир:** иначе игрок, сыгравший один турнир 100-0, а все остальные проваливший (не выходя из группы), получил бы незаслуженно высокий peak. Окно требует устойчиво высокой формы на протяжении месяцев.
- **Порог выборки:** окно засчитывается только при `games ≥ N_min`, иначе не считается пиком.
- В `ratingModelVersion=v1.1.0`: окно — **120 календарных дней включительно**, `N_min=15`. Пересчёт выполняется во все даты, когда матч входит в окно или выходит из него; это эквивалентно ежедневному rolling-проходу без пустых повторных вычислений.
- Peak хранится отдельно по каждой роли. При одинаковом OVR выбирается окно с большим числом игр, затем более раннее окно — результат не зависит от порядка входных данных.
- Параметры окна и `N_min` версионируются; изменение требует новой `ratingModelVersion`.

#### 5.4.3. Team-Success Rating (для Mixed Draft) 🆕
В режиме **Mixed Draft** игрок оценивается **по успеху его команды за окно** (1/2/5 лет — ось Format), а не по индивидуальной форме на событии:
- Базовые сигналы за окно: **placements** на тир-1 ивентах (веса по престижу: TI > Major > прочее), **призовые**, **винрейт** команды, кол-во топ-финишей.
- Итог: `PlayerScore = f(TeamSuccess за окно) · g(индивидуальная форма)` — команда-успех как основной множитель, инд. форма как поправка (чтобы «пассажир» чемпионского состава не весил как его кор).
- Если игрок за окно поиграл в нескольких командах — агрегируем по времени, проведённому в каждой (weighted by games/сроки).
- Формула и веса версионируются, тюнинг на данных (§10-C).

В `ratingModelVersion=v1.2.0` для каждого `last_1y/last_2y/last_5y`:

- `PlacementScore = clamp(25 · Σ prestige(event) · placementValue)`;
- prestige: **TI=3, Major=2, tier-1=1**;
- placement value: **1-е=1.00, 2-е=0.65, top-4=0.40, top-8=0.15**;
- `PrizeScore = clamp(100 · log1p(prizeUsd) / log1p(10 000 000))`;
- winrate для формулы сглаживается как `(wins + 10·0.5)/(games+10)`, а в `teamSuccess.json` сохраняются сырой `winrate` и `games`;
- `TopScore = clamp(titles·30 + top4·10)`;
- `TeamSuccess = 40% Placement + 20% Prize + 25% Winrate + 15% TopScore`.

Для игрока: сначала успех его команд усредняется по числу сыгранных за них матчей, затем умножается на ограниченную поправку индивидуальной формы: `factor = 0.8 + 0.4·IndividualOVR/100` (диапазон `0.8–1.2`, OVR 50 нейтрален). Итог ограничивается `0–100`. Неизвестный `teamId` — ошибка контракта, а не нейтральный fallback. `valve_legacy` требует отдельного курируемого набора TI/Valve Major и в эту временную агрегацию намеренно не входит.

##### Что из этого реально работает (статус 2026-07-19)

Формула выше описывает **целевую** модель. Фактически подключено:

- ✅ **Mixed использует team-success, а не event OVR** (`web/src/game/teamSuccess.ts`, `ratingModelVersion v1.11.0`). Team Packs не затронут — golden `engine-run-team` проходит байт-в-байт.
- ✅ Поправка на индивидуальную форму — дословно `0.8 + 0.4·OVR/100`, покрыта тестом.
- ⚠️ **`successScore` — прокси, а не формула v1.2.0.** Данные приходят из `domain.BuildTeamSuccess` = сглаженный winrate × вес тира лиги. Компоненты «плейсменты 40% + призовые 20% + топ-финиши 15%» в данных **нулевые** (проверено: 417 записей окон, `titles`/`topFinishes`/`prizeUsd` = 0 во всех) — они выводятся из Liquipedia, а **T1.3 ⛔**. Полная реализация лежит в `pipeline/internal/teamsuccess`, но не подключена к `domain.Build`. UI об этом говорит честно: легенда Base в Mixed пишет «винрейт с поправкой на тир лиги», а не «плейсменты и призовые».
- ⚠️ **`valve_legacy` в Mixed закрыт SOON**: 0 команд из 131 имеют team-success в этом окне. Гейт (`mixedSupportsFormat`) смотрит на данные, а не на имя формата, — окно наполнится, режим откроется сам.
- **Отображение в игровую шкалу — на фронте, не в пайплайне.** Сырой `successScore` живёт в своей шкале (медиана 32, 15.6–54.7), а игровая — event OVR (медиана 74) и боты `Normal(86,5)`; подстановка сырого числа дала бы Team OVR ~38 и гарантированный проигрыш. Полоса `48..76` калибрована по **реализованной** медиане Team OVR (60 забегов на стиль): Team Packs 78.3, Mixed 76.8 — ни один стиль не доминирует. Существенно поменяются данные — перепроверить тем же замером.

### 5.7. Hero Synergy — games-driven назначение (реконструкция 322-0, v1.5.x)
Проверено по данным 322-0 (2026-07-15): синергию определяет **число pro career-игр игрока на герое** («more games is better»), НЕ winrate. У пар химии `winrate=0.000`, а бонус ненулевой ⇒ модель games-driven.
- **Приоритет матчинга — число игр** (`assignmentPairScore = games·1000 + winrate`, winrate — лишь tie-break): «больше игр — лучше» (наблюдалось: Void Spirit переехал с игрока с 7 играми на игрока с 30). Назначение 5 героев 5 игрокам — **задача о назначениях** (венгерский). Automatic ре-оптимизирует всё назначение при каждом новом игроке; остаточному игроку может достаться герой с 0 игр. Роль героя назначение **не** ограничивает (у референса так же). Manual — игрок сам.
- **Итог — сумма вкладов по пятёрке, не среднее.** Каждый назначенный player×hero добавляет вклад (насыщается по играм: мало pro-игр → ≈0, много → к капу), поэтому добавление игрока увеличивает синергию. Пороги подписей ≈ GREAT +4 / INSANE +7.
- **Источник — pro career all-time** (`careerPlayerHeroStats`: агрегат из tier-1 pro match details, **без pub**). OpenDota `/players/{id}/heroes` **не используем** — pub+pro давали absurd picks (support с carry-героем из pub) и завышенные счётчики (1400 «игр» на Timber). `playerHeroStats` — то же, но только в rolling-окне (recent form). Глубина этих данных прямо определяет силу синергии.
- Во время незавершённого драфта считаются только уже назначенные пары; игрок без героя не создаёт штраф. Каждый пак предлагает ровно 5 ещё не взятых героев (пересечения добираются из format-pool детерминированно).
- **Разделяй assignment и отображение:** matching/score — по pro-window (`heroStatsForAssignment`), а «N games» в UI — по pro career all-time (`heroStatsForDisplay`). Клик по игроку открывает event-scoped и career player×hero `{games, winrate}`.

### 5.8. Chemistry — пожизненные попарные co-games 🔄
- **Основной сигнал — пожизненная сыгранность любых двух игроков состава**, а не только пар из одного пака. Подтверждено на 322-0: `Saksa + Watson · 185 games · +0.8` сработало для игроков, взятых из **разных** паков (Digital Chaos и Cloud9) — связь по совместной карьере на tier-1. UI показывает попарно `Игрок A + Игрок B · N games · +бонус`.
- **Формула v1.13.0:** бонус пары = `min(4, games / 230)`, НЕ winrate пары (в данных 322-0 winrate пар = 0 ⇒ считается по co-games). Chemistry = сумма максимум десяти **уникальных пар** пятёрки с общим cap `13`; current/former-множителей и baseline «состоят сейчас в одной команде» нет.
- Группы из 3–5 игроков остаются в `squadSynergy` как исторический агрегат, но **не складываются поверх собственных пар**. Предыдущий учёт пар + вложенных троек/четвёрок повторял одни связи и преждевременно насыщал cap: рыночная замена на игрока с реальными co-games могла не менять Chemistry.
- **Требование к данным:** сигнал живой только на **мульти-эвентном tier-1 датасете** с пожизненной матрицей co-games (`/players/{id}/peers` + агрегация pro-матчей). На срезе одного турнира кросс-командных пар нет → химия структурно ≈ 0; production refresh уже собирает пожизненные пары для всей pro-вселенной.
- Промежуточная Chemistry — накопительная проекция относительно 10 возможных пар полной пятёрки: новые сыгранные пары постепенно добавляют вклад. Для итоговых пяти игроков масштаб совпадает с формулой полной пятёрки.
- Игровой клиент не запрашивает OpenDota/Liquipedia во время драфта: справочник героев, player×hero и пары заранее собирает resumable Go ETL и публикует как versioned `public/data/*.json`. Runtime-БД для этих данных не нужна; расширение last_2y и scheduled refresh остаются задачей пайплайна.

### 5.9. Полный Roguelite Run 🟨
Первый исполняемый вертикальный цикл Classic реализован: после 5 пиков игроков + 5 пиков героев пользователь получает прогноз против поля из 18 команд, проходит две группы по 9, double-elimination плей-офф, Grand Final BO5 и итоговое место. Поле и все матчи воспроизводимы по `seed + dataset version`.

> **UI-статус 2026-07-12 (правки в рабочем дереве, деплой пользователем):** соперники Classic — **фэнтезийные боты** со случайными именами (реальные команды — режим Real Tournament); итог драфта ведёт в турнир кнопкой «Start tournament» (без «New run»/preview/seed); стадии `field → groups → playoffs`, где playoffs — **терминальный экран** (место + чемпион + сетка UB/LB с Grand Final + итоговая таблица + твой состав/герои/синергия/химия) — всё на одном экране, как в 322-0. **Осталось (P0): live-симуляция как процесс** — group stage «LIVE» + Skip, пораундовое раскрытие сетки/таблицы (сейчас результат считается мгновенно, экран лишь раскрывает готовое). См. BACKLOG `TREF-TOUR1`.

`TournamentEngine` — отдельный чистый orchestration-слой поверх результата драфта: он не расширяет `RunEngine` и не меняет формулу `Team OVR`. Группа — круговой BO2 (16 карт на команду); топ-4 идут в upper bracket, 5–8 — в lower, девятая команда вылетает. Итоговые диапазоны соответствуют точке вылета из double-elimination сетки. Прогноз ранжирует сырой OVR, а матч использует логистическую вероятность, поэтому фаворит может проиграть, но seed всегда даёт тот же результат.

Оставшаяся roguelite-арка — экономика, награды, Camp/Market, build-defining решения и boss conditions между турнирными этапами:

Полный забег строится как Dota-турнир из последовательных этапов:

1. **Draft** — собрать стартовый ростер и пул героев.
2. **Stage** — пройти реальную турнирную структуру (Group Stage → double-elimination Playoffs → Grand Final).
3. **Reward** — получить валюту и выбрать одно улучшение/перестройку.
4. **Market / Camp** — купить тактику, расширить hero pool, заменить игрока или подготовиться к следующему условию.
5. **Boss Stage** — особое правило, меняющее оптимальную сборку, а не просто больший числовой порог.
6. **Season Win / Loss** — промах порога завершает забег; победа на последнем этапе сезона (целевая структура — Stage 25, §5.9.3) — терминальная победа. 🔁 *Формулировка «первое чемпионство закрывает вступительный круг, но не сам забег» superseded §5.9.3.*
7. **Dynasty Loop** — **добровольное** продолжение после победы в сезоне: бесконечные круги с растущей силой поля и Stakes, пока не проиграет. Уже засчитанную победу поражение в Династии не отменяет.

Сложность поля и специальных условий должна расти быстрее базовой силы состава, поэтому игрок обязан строить синергии, а не просто выбирать максимальный OVR. Seed определяет паки, поле, матчи, будущие рынок и награды целиком.

#### 5.9.1. Режимы забега

1. **Classic.** All-time fantasy draft; текущая механика. Внутри выбирается `Team Packs` или `Mixed Draft`, затем состав проходит турнирную арку. Это базовый и самый прозрачный режим.
2. **Esports Manager.** Игрок принимает организацию в выбранном регионе, работает с контрактами/бюджетом, собирает доступный ростер и идёт через квалификации и сезоны. В отличие от Classic, ценность игрока определяется не только OVR, но и стоимостью, сроком контракта, регионом и развитием. Точные правила — отдельная продуктовая спека ([docs/modes-scenarios.md](modes-scenarios.md), BA-черновик 2026-07-12); режим не должен быть просто Classic с другой обложкой.
3. **Real Tournament.** Игрок выбирает реальное событие **списком** (RT-A, решение 2026-08-19; каталог — события с полным полем ≥17 реальных составов), заранее видит его поле; сид решает симуляцию и паки challenger-драфта, а не состав поля. Все игроки события получают **roster lock** и исключаются из пользовательского draft pool. Пользователь собирает challenger-команду из игроков вне турнира: исторических легенд, свободных агентов и игроков других эпох/сцен (пул = пак-снапшоты выбранного формата, RT-C). Затем играет против фиксированного поля через группы, плей-офф и финал. Реализация (срез 1, 2026-08-19) — `TournamentEngine` с реальными `packs` как opponents + roster lock через draft-исключения `RunEngine`; сценарий — [docs/modes-scenarios.md §2](modes-scenarios.md), статус — BACKLOG T5.6.
4. **Roguelite Run.** Полная ante-арка §5.9 как **отдельный режим** рядом с Quick Draft. Драфт пятёрки — один раз (та же механика Classic), дальше ростер **персистит** и проходит **последовательность этапов с растущим порогом места**; промах порога = конец забега (роглайт-смерть), между этапами — награда и рынок/лагерь для усиления. Не форк Classic и не новый движок счёта: тонкий stage-orchestration-слой поверх `RunEngine`/`TournamentEngine` (скилл `game-state-architecture`). Продуктовое решение и раскладка — §5.9.2.

Правила Real Tournament:
- eligibility считается по каноническому `accountId`, а не по нику; один человек не может одновременно быть у соперника и пользователя; лочится событие **целиком** (все его составы, не только топ-17 поля);
- snapshot включает event id, дату отсечки, команды и их заявленные ростеры; поздняя замена/stand-in учитывается только если входит в выбранный snapshot;
- opponent field, draft pool, рынок и матчи полностью воспроизводимы по seed + dataset version; поле турнира — производная данных (топ-17 составов события по честной оценке `scoreTeam`), сид на него не влияет; реролла поля нет;
- **подготовка к событию (RT-E, 2026-08-23):** между драфтом и посевом — одна детерминированная фаза с фиксированным бюджетом недель сборов (`PREP.budget`), без золота/рынка/предметов/множителей: **сыгровка** пары (виртуальные co-games → Chemistry по той же кривой) и **тренировка героя** (виртуальные игры игрок×герой → Hero Synergy по той же кривой); бонусы идут в те же слагаемые Team OVR, что считают поле, поэтому честность поля сохраняется. Третий рычаг — **разбор соперника** (срез 2): неделя на демки одного состава поля режет его Hero Synergy на 50% (не больше двух составов; свой счёт не меняется; поле пересчитывается теми же 17 составами). План — часть лога действий забега (replay/resume); сид по-прежнему решает только симуляцию. Замер и числа — BACKLOG T5.6, срезы 4–5;
- **сила реального состава = Base + Hero Synergy, без Chemistry (RT-D, 2026-08-23):** event-OVR состава уже содержит игру с этими тиммейтами, а Chemistry — драфт-механика «собери сыгравшихся», челленджеру структурно недоступная (сыгранные топ-коры залочены событием); с Chemistry поле топ-событий давало 0% побед и треть последних мест, без неё челленджер — андердог с шансом (замер в BACKLOG T5.6, срез 3). Сила поля (медиана/лидер) показывается при выборе события: выбор события = выбор сложности;
- исторический игрок оценивается своей формой выбранной эпохи, а не сегодняшним состоянием (RT-B: без нормализации между эпохами; challenger-пак mixed по механике, но base — event-снапшоты, не team-success);
- **реальный исход не реплеится**: placements отложены до Liquipedia, поэтому UI обязан подавать результат как «симуляцию против реального поля», а не «как было»;
- если после roster lock нельзя собрать валидную пятёрку ролей, генератор обязан сменить snapshot/pool или завершиться понятной ошибкой, но не ослаблять lock молча.

#### 5.9.2. Roguelite Run — продуктовое решение (2026-07-22)

**Quick Draft остаётся.** Текущий Classic (5 пиков → один турнир → место + карьера) — это Quick Draft из §6.2: короткий, вылизанный, самостоятельный режим со своими golden-тестами. Он **не переделывается и не прячется** — Roguelite Run добавляется рядом как отдельный пункт мод-шелла (`selectedMode`), переиспользуя Quick Draft как кирпич (один этап = один `TournamentEngine`).

**Бесконечная фаза «Династия» (решение после playtest 2026-07-23).** Пять этапов — не полный забег, а первый круг и понятная цель для нового игрока. Победа на этапе 5 фиксирует первый Aegis/титул, выдаёт milestone-награду и после Буткемпа запускает следующий круг в **том же забеге**. Отдельный режим и повторный драфт не создаются: сохраняются активный ростер, резерв, hero pool, золото, Tactics и Camp Actions.

- **Круги по пять этапов, абсолютный Stage без лимита.** Внутри каждого круга повторяется читаемая лестница `топ-10 → топ-6 → топ-4 → топ-3 → 1-е`, но базовая угроза всего поля растёт от круга к кругу. UI после первого титула показывает, например, `Stage 12 · Dynasty 3 · 2 Aegis`, а не ложное `12/∞`.
- **Два независимых источника сложности.** Внутри круга действует знакомая локальная рампа, между кругами добавляется постоянный `dynastyThreat`; boss conditions/Stakes меняют правила и экономику, а не только OVR. Формула будущей реализации: `fieldBoost = openingOffset[stageInCycle] + cycle·dynastyStep`, где `dynastyStep`, частота боссов и набор Stakes определяются симуляцией T6.3, а не подгоняются под один скриншот.
- **Команда растёт до конечного потолка, угроза — нет.** Вертикальная сила забега ограничена реальным пулом игроков, максимальной редкостью героев, caps эффектов, пятью общими слотами Tactics/Items и двумя слотами Camp Actions. Бесплатные плоские `+N OVR` не могут копиться бесконечно; после заполнения билда награды становятся заменами, sidegrade, экономикой или reroll. `dynastyThreat` продолжает расти без верхней границы, поэтому любой забег в итоге заканчивается поражением, но не на заранее заданном номере этапа.

Лестница качества намеренно конечна и останавливается (`R12.4`), а добавление `Divine`/`Ancient` поверх `Immortal` только отложило бы тот же потолок. Новая глубина берётся из **второй, ортогональной оси: модификатора ПОВЕДЕНИЯ карточки**, а не величины её эффекта. Тир отвечает на «насколько сильно», модификатор — на «как именно работает» (например: растёт вместе с выполнением своего условия до конечного потолка; усиливается ценой риска; иначе переживает давление боссa). Правило прежнее и не смягчается: ни один такой модификатор не даёт неограниченного числового роста, у каждого есть либо потолок, либо цена.
- **Экономика не должна убегать в бесконечность.** После первого круга выплаты, цены и sinks масштабируются по номеру Dynasty; лишние/повторные карточки конвертируются по ограниченным правилам. Большой запас золота расширяет выбор, но не покупает бесконечный uncapped Team OVR.
- **Титул Династии = токен зачарования (LG6, 2026-08-24).** Milestone-награда круга платит той осью, которой в Династии ещё есть куда расти: игрок вешает Edition (Charged/Tempered) на карту без Edition. Золото/качество к этому моменту мертвы по замеру (качество на максимуме у 97%, слоты полны); Edition-токен растит билд в рамках существующих потолков (слоты × 1 Edition, заряды капятся по тиру) и синергирует с trade-in: новая карта приходит чистой, отложенный токен снова находит цель. Замер — BACKLOG R10/LG6.
- **Stakes = те же мутаторы, добровольно и на весь сезон (T6.4 срез 1, 2026-08-25).** Одна система правил сложности: стартовый Stake выбирается в Особых правилах из определений мутаторов кругов, действует на все этапы сезона (в Династии — только мутатор круга, стек правил не заводится). Открывается первой честной победой сезона (cheat не открывает и не совместим); входит в RunConfig/ссылку/сейв/карьерную метку; постоянного `+OVR` не даёт — награда сверх метки в карьере остаётся открытым вопросом. Замер и статус — BACKLOG T6.4.
- **Все четыре правила — рабочая лестница тяжести (b1.41.0, 2026-08-26).** Немые в сезоне правила перепроектированы формой: `uncappedBoss` — правила боссов судят все турниры выше обычных (elite/playoffCheck/финал) без потолка штрафа; `doubleBans` — вне финалов каждый турнир судится ротирующимся heroBan-листом (реролл правила пересматривает список). Лестница по замеру (база 31.3%): 27.7 / 27.7 / 25.0 / 23.3. Принцип, подтверждённый двумя откатами: **ставки строятся на судимых осях (пороги, цены, штрафы), а не на сокращении снабжения** — supply-правила не измеряются сим-агентом (не оптимизирует драфт героев), а для игрока меняют знак эффекта непредсказуемо. Детали — BACKLOG T6.4.
- **Комбинации Stakes и награда сверх метки (T6.4-2, 2026-08-26).** `RunConfig.stakes` — список; лестница прогрессии: победа сезона → Stakes, победа со ставкой → комбинации. Все четыре разом — 16.3% (замер) — «золотая ставка» без отдельного механизма уровней. Награда за сыгранные ставки — метки мастерства «✓ пройдено ×N» на самих правилах (производная карьеры, без нового хранилища и без +OVR).
- **Первый Aegis — milestone, Loss — единственный штатный финал.** Career хранит максимальный абсолютный Stage, число выигранных Aegis-кругов, финальную силу/билд и причину поражения. Resume восстанавливает любой номер этапа; `seed + dataset + balanceConfigVersion + абсолютный stage` воспроизводят поле, награды, рынок и boss conditions.
- **Цель баланса, не жёсткий лимит.** Обычная удачная сборка должна увидеть второй круг, сильная — пройти несколько Dynasty, исключительная — уйти на 20+ этапов. Точный профиль выживаемости фиксируется только массовой симуляцией; архитектура не содержит `stageCount = 5` как условие победы.

Причина не «сделать легче», а измеренная разница источников роста: сила билда прибавляет за акт `1.53 / 1.50 / 1.24 / 1.26 / 1.05` по актам сезона и **1.007** в Династии — там слоты полны, качество на максимуме, и билд живёт заменами (это и есть «конечный потолок» из пункта выше). Отдельный шаг не отменяет безграничности угрозы (штатный финал по-прежнему Loss) и не трогает сезонную полосу 30–40%. Числа и A/B — BACKLOG R10.

**Прогрессия = докидываем в существующую формулу `Team OVR = Base + Hero Synergy + Chemistry`.** Каждая покупка на рынке поднимает одно из трёх слагаемых, у каждого свой trade-off (чтобы усиление не сводилось к «числа побольше»):
- **Base** — заменить слот на игрока сильнее по OVR (ломает химию/хиро-синергию этого слота); аренда стенд-ина на этап.
- **Hero Synergy** — открыть игроку сигнатурного героя / расширить пул (точечно, без ломки состава).
- **Chemistry** — купить игрока по co-games с текущей пятёркой (`squadSynergy`), а не по OVR: «синергия дороже суммы».
- **Tactics (пассивки)** — отдельный слой сверх формулы: постоянные модификаторы в ограниченных слотах (общий регион/эра, сыгранные пары, широкий пул, comeback) — задают билд-архетипы. Вводятся **после** экономики (см. §5.10).

**Экономика наград v1 (решение после playtest 2026-07-23).** Награда больше не плоская между этапами. Автоматические призовые = растущая база `3/4/5/6` золота за этапы 1–4 + бонус `0…3` за место лучше текущего порога. Бонус считается по **относительному** пути от порога к первому месту: победа даёт одинаковый cap `+3` и при top-10, и при top-3, поэтому широкий ранний порог не печатает больше денег, чем поздний. Золотые Reward-карты тоже растут: little `3/4/5/6`, large `6/8/10/12`. Цены рынка пока фиксированы — поздний этап сознательно даёт больше свободы перед финалом; точная инфляция и sink-баланс калибруются массовой симуляцией T6.3.

**Резерв v1 (реализован 2026-07-23).** Структурная покупка сразу меняет активный слот, а снятая сущность не исчезает: каждый снятый игрок добавляется на скамейку, герой уходит в резервный пул до трёх героев. В последующих Буткемпах любого запасного можно бесплатно вернуть в подходящий активный слот; снятый активный игрок, в свою очередь, остаётся на скамейке. Новые покупки не вытесняют ранее полученных игроков, поэтому забег постепенно собирает собственную коллекцию вариантов состава; hero pool при этом остаётся ограничен тремя последними снятыми героями.

**Интерфейс перестройки (решение после playtest 2026-07-23).** В Буткемпе состав нельзя сворачивать до трёх абстрактных чисел: рядом с решениями постоянно видны radar-пентагон активной пятёрки, назначенные герои, Hero Synergy и Chemistry-связи. Рынок всегда показывает два самостоятельных пака по пять карт: пять замен игроков и пять разных hero re-pick; общий reroll обновляет оба. Замена игрока показывает компактную карточку реального входящего `accountId` с ролью, командой, `IMP/ECO/REL/OVR`, назначенным героем и полным пересчётом `до → после`. Целевой слот выбирается по максимальному итоговому Team OVR среди всех активных игроков той же роли; особенно это важно для двух support-слотов, поэтому оба support-оффера могут честно предлагать заменить одного и того же игрока. Hero-карта строится вокруг **входящего** героя: для него перебираются все пять возможных удалений из активного пула, Hungarian matching заново оптимизирует назначения, а карточка показывает лучший по итоговому Team OVR вариант — кого герой заменит, кому будет назначен и сколько у этого игрока игр на нём. Несколько входящих героев вправе оптимально вытеснять одного и того же слабого героя; случайное сопоставление «по позиции в массиве» запрещено и для игроков, и для героев. Карта также показывает изменение Team OVR и всех затронутых слагаемых; эта структура остаётся основой для будущих rarity/quality-бонусов. Выход запасного всегда читается в направлении **резервный/входящий → активный/заменяемый** и заранее показывает конкретную пару и точный прогноз; после клика немедленно меняет radar. Выбранный активный состав обязан переживать переход к следующему этапу и resume.

**Редкость героев (решение 2026-07-22).** У героев в паке — ступени редкости `common / unique / mythic / immortal` (по-дотовски, с цветом), каждая несёт «пакет» бафов (как edition в Balatro): выше редкость — больше вклад. **Зачем:** сейчас героев назначает венгерский матчинг авто-оптимально, поэтому пик героя низкоставочный; редкость возвращает агентность («блестящий mythic вне синергии vs обычный в паре»). Правила:
- **Скоуп — только Roguelite Run.** Quick Draft играет обычными героями: иначе поедут golden и придётся бампать `ratingModelVersion`. Rarity — модификатор режима, не датасета.
- **Канал бафа — Hero Synergy** (свойство героя): редкость даёт растущий бонус к вкладу назначенного героя; у `immortal` — плюс маленький `+OVR` игроку, который его запикал (Base).
- **Источник — ролл ИЛИ рынок:** редкость роллится на слот пака по seed (ранние этапы — почти всё common, высокие — mythic/immortal как лут прогрессии), **и** её можно поднять покупкой на рынке («заколдовать» героя).
- **Реролл ≠ улучшение (решение 2026-07-23).** На рынке героев два **разных** действия: **реролл** заменяет героя в слоте на другого (можно встретить как common, так и выше по качеству), **улучшение** поднимает качество текущего героя. Реролл никогда не улучшает того же героя; поднять качество можно **только** улучшением. Повторный клик по тому же герою его не «прокачивает».
- **Гейт мета-прогрессии (решение 2026-07-23, 🔁 уточнено 2026-07-27).** Самый первый забег игрока — весь на common/серых героях без **случайных** эффектов (чистый вход). ~~Редкость, улучшение и реролл качества открываются со второго забега~~ → **ручное улучшение качества в Буткемпе доступно с первого забега**; мета-гейтом закрываются только случайные дропы повышенного качества (§5.9.3, «Разделение флагов редкости»). Гейт остаётся мета-анлоком Штаба (см. §5.10, T6.4), а не внутри-забеговым правилом.
- **Детерминизм/контракт:** редкость роллится по seed в самом забеге, **не** пишется в `heroes.json`/`schema`; герой не «mythic глобально», а mythic в этом паке этого забега.
- **Нейминг/визуал:** отдельный неймспейс токенов `--rarity-*`, переиспользующий фольга/частицы-утилиты каст-эджа (T7.9), семантически не смешивая с OVR-тиром игрока `--tier-*` (там `immortal` уже занят).

**Боссы** обесценивают один рычаг и заставляют вложиться в другой (химия отключена → мёртв химия-стак; нет игроков >85 OVR → мертва звезда; пул героев вдвое → бьёт по флексу) — так ни одна сборка не доминирует.

**Порядок срезов (наращиваем мясо на скелет):** (1) петля дышит — 2 этапа + растущий порог + смерть + растущее поле, ростер персистит, без экономики; (2) экономика — призовые + жетоны реролла + рынок с заменой слота; (3) рычаги Hero Synergy/Chemistry на рынке; (4) тактики-пассивки малым курируемым набором; (5) боссы; (6) бесконечная Dynasty-фаза без терминальной победы на пятом этапе. Экономика и тактики — отдельные валюты/слои (§5.10); каждый срез играбелен сам по себе.

#### 5.9.3. Roguelite Run — конечный сезон и Balatro-парити (решение 2026-07-27)

Источник: [docs/roguelite-balatro-brief.md](roguelite-balatro-brief.md) (бриф + ревизия при приёмке с проверкой каждого утверждения по коду). Декомпозиция — BACKLOG **M5R** (`R1…R10`). Balatro используется как референс **принципов**, а не как шаблон интерфейса: конечный основной забег + добровольный Endless, редкая ранняя находка, статичные базовые цены, дорожающий reroll, ограниченные слоты, аддитивные и мультипликативные слои, заранее видимые боссы, Stakes.

**Quick Draft не переделывается.** Всё ниже живёт только в roguelite-слоях либо является чистым presentation shortcut. Не меняются: `scoreTeam`, `ratingModelVersion`, генерация пула, экономика/тактики/боссы Classic, поле турнира Quick Draft, golden-фикстуры. Общими могут быть только переиспользуемые UI-компоненты, optional-поля конфига с default `false` и локализация.

**Один Stage = один полноценный турнир.** Переход на одиночные матчи отклонён: он потребовал бы второго движка, экрана, набора наград и тестов ради того, что уже работает. Турнир играет роль Blind: проверка подготовленного билда → результат → награда → магазин.

##### Структура сезона

`5 актов × 5 этапов = 25 турниров`. Это **стартовая продуктовая гипотеза** (кандидаты A/B — 20 / 25 / 30), а не константа: точное число подтверждается симулятором `R10`, архитектура не должна содержать «25» как условие победы иначе как через конфиг акт-модели.

| Акт | Этапы | Содержание |
|---|---|---|
| 1 · Open Qualifiers | 1–5 | Знакомство с экономикой, первое направление билда |
| 2 · Regional Circuit | 6–10 | Более сильные формы игроков, первые устойчивые комбинации |
| 3 · Major Circuit | 11–15 | Нужен не только высокий OVR, но и работающий архетип |
| 4 · Elite Circuit | 16–20 | Сильные sidegrade; боссы бьют по ключевым механикам билда |
| 5 · The International | 21–25 | Финальная проверка состава, экономики и билда |

Шаблон акта: этапы 1–2 — Regular, 3 — Elite (усиленное поле, но не босс), 4 — Playoff Check, 5 — **Boss Tournament**. Боссов ровно пять на сезон, последний — Showdown Boss. Это отменяет текущее `BOSS_FIRST_STAGE = 2` (босс на каждом этапе с третьего).

> ✅ **Реализовано 2026-07-29 (`R6.1`).** Шаблон живёт в `game/anteRun.ts::SEASON_TEMPLATE`, длина акта выводится из него, длина сезона — параметр `buildSeason({ acts })`, поэтому «25» нигде не является условием победы: симулятор сравнивает 20/25/30 тем же кодом, каким играет игра. «Усиленное поле» Elite реализовано надбавкой `ANTE_THREAT.elite` (плейсхолдер, калибровка — `R6.4`); тип этапа виден игроку бейджем рядом с «Акт N · Этап M», иначе усиление поля было бы невидимой механикой.

##### Пороги мест — только реальные бакеты

Порог этапа задаётся **worst-rank существующего placement-бакета**. Легальные значения: `1, 2, 3, 4, 6, 8, 12, 16, 17, 18`. Любое другое число даёт ложную подпись — сегодня `target = 10` требует фактического топ-8, потому что бакет `9-12` не проходит. Инвариант закрепляется тестом, а не разовой правкой цифры.

Обычный этап требует конкурентоспособности, а не чемпионства; финалы актов ужесточаются: `Stage 5 → топ-4`, `10 → топ-3`, `15 → топ-2`, `20 → топ-2`, `25 → 1-е (Showdown)`. Место выше порога не влияет на проход, но даёт дополнительную ценность (золото / улучшенный reward roll / трофей).

> ✅ **Уточнено замером 2026-07-29 (`R6.4`, ответ на §10.I).** Порог Stage 20 был `1-е` — то есть чемпионство требовалось дважды за сезон. Замер (`npm run sim -- 60 --finales`, общие сиды): требование чемпионства на S20 роняло проходимость этого этапа у билд-забегов с 93.5% до 83.9%, у жадных — с 62.1% до 48.3%, при **неизменном** общем win-rate 30.0%. То есть оно не добавляло сложности, а переносило точку обрыва в середину сезона: 20 сыгранных турниров терялись на одном BO5. Теперь чемпионство требуется ровно один раз — на Stage 25, где за ним ничего не теряется. На Stage 20 первое место оплачивается премией `prizeForStage` (максимум `prizePerformanceMax`) — это и есть «чемпионство как бонус».

##### Победа и Династия

Победа на Stage 25 — **терминальное состояние** `phase = "won"`. Экран результата показывает сезон, финальный Stage, титулы, состав, качества героев, Tactics/Items, Tournament Power, ключевые синергии, использованный Stake и отметку Cheat Mode. Дальше игрок выбирает: **завершить забег** или **продолжить в Династии**. Продолжение не отменяет уже засчитанную победу — поражение в Династии записывает, что основной сезон выигран.

Династия сохраняет весь ростер и билд, продолжает растить threat, всё чаще предлагает sidegrade вместо апгрейда, выдаёт milestone каждые пять этапов и не имеет верхнего cap поля — она заканчивается только поражением.

> ✅ **Реализовано 2026-07-29 (`R6.3`).** Победа сезона терминальна и **банкуется сразу** — career-запись пишется в момент победы, не дожидаясь выбора: сам факт от решения не зависит, а вкладку могут закрыть на экране итога. Продолжение в Династии — тот же забег (ростер, билд, золото), просто за концом сезона: правила этапа там считает та же арифметика актов, что и внутри сезона (`seasonStage` работает за пределами `stages`), а `seasonWon` — липкий флаг, поэтому поражение в Династии победу не отменяет. Глубина Династии пишется **отдельной** career-записью с меткой `dynasty`, которая, как и cheat-записи, не идёт в агрегаты и в счётчик забегов: один забег не должен считаться дважды. Второй «победы» в бесконечной фазе нет — её штатный финал только поражение.
>
> ✅ **Контент Династии 2026-07-29 (`T5.8`).** Каждый пройденный акт ЗА пределами сезона даёт **титул** с наградой (золото + готовое улучшение качества героя). Внутри сезона титула нет: там финал акта уже оплачен растущими призовыми и премией за место (`R6.4`). Счётчик титулов выводится из индекса этапа, а не хранится отдельно.
>
> 📊 **Замер (`npm run sim -- 60 --dynasty`, симулятор теперь играет Династию до глубины 25).** Билд-агент доходит до Династии в 18 забегах из 60 и живёт там **медиана 8 этапов, p90 = 19**. То есть продолжение само по себе длинное — гипотеза «осмысленно на пару этапов» замером НЕ подтвердилась. Подтвердилось другое: **рынок в Династии почти мёртв — 0.18 покупки на лагерь против 0.90 в сезоне** (127 замеренных лагерей). Это не дефект правил, а прямое следствие конечного контента (пул игроков конечен, редкость героев и тир карточек имеют максимум) — ровно то, что §5.9.3 и закладывала. Титул закрывает вопрос «что здесь делать», но не возвращает рынку смысл: для этого нужны поздние синки (booster packs, снятие негативных свойств, boss reroll, premium scouting), а не новое правило рынка.
>
> ✅ **Синки реализованы 2026-07-29 (`T5.9`, см. ниже в §5.9.3).** Диагностика уточнила диагноз: рынок на глубине не «мёртв», а **насыщен** — карты есть (9.4 на лагерь), но лучшая даёт +0.18 Team OVR при 836 золота на руках, качество героев на максимуме в 95% лагерей, слоты полны в 100%. Поэтому booster packs из списка выше отброшены, а сделаны расходуемые покупки. Замер A/B: **глубина Династии не изменилась** (p50/p90 = 5/15) — синк возвращает лагерю решение, а не растягивает забег; смертность под боссом при этом упала вдвое (24.7% → 11.3%).
>
> ⚠️ **Известное ограничение:** выбор «завершить / продолжить» живёт в сессии. Сейв на победе очищается (забег терминален), поэтому перезагрузка на экране итога оставляет победу засчитанной, но продолжить Династию уже нельзя. Сама Династия, если её выбрали, персистится и возобновляется штатно (`anteStageIndex` за пределами сезона + `anteSeasonWon`).

##### Сила поля: параметризация вместо «сдвиг-и-кламп»

Текущая модель `clamp(76, 99, sample + fieldBoost)` ломается на обоих концах. Замер (20k сэмплов на этап) показал, что на **первом этапе 90.2% поля стоит ровно на 76** (`sd = 0.99`): распределение схлопывается в спайк, матчи ботов между собой становятся монетками, и место игрока определяется жеребьёвкой, а не силой — отсюда «~1/3 наивных забегов гибнет уже на этапе 0» из прогона T6.3. Верхний кламп `99` — та же болезнь с другой стороны: он станет обязывающим на длинном сезоне и в Династии, когда `fieldBoost` уйдёт в плюс.

Решение: **Quick Draft оставляет шкалу `76–99` без изменений** (она подтверждена golden и parity-аудитом), а Roguelite Run параметризует поле по этапу — `mean(stage)`, `sd` — и не применяет терминальный кламп к итоговой силе соперника:

```
opponentRosterQuality  : 60–99 (качество ростера — остаётся ограниченным)
opponentTournamentPower: без cap — rosterPower · teamMult · xMult + actThreat + bossThreat + stakeThreat
```

Высокий win-rate нельзя лечить одной длиной забега: его причины — стартовый гандикап, оба клампа, неучтённые build-системы, отсутствие late-game scaling и текущие пороги. Длительность, вероятность победы, рост силы, экономика и Stakes калибруются **раздельно**.

##### Team OVR ≠ Tournament Power

`Team OVR = Base + Hero Synergy + Chemistry` остаётся читаемой оценкой **объективного состава** — предметы и множители его не умножают, иначе рейтинг игроков теряет смысл. Сила roguelite-билда выносится в отдельную величину:

```
rosterPower     = teamOvr + flatPower
teamMult        = 100 + additiveMult
tournamentPower = rosterPower · (teamMult / 100) · Π xMult
```

UI показывает слои раздельно (`Team OVR 108 · Additive +24 · X Mult ×1.35 · Tournament Power 178`). Типы эффектов: flat (сильны рано), scaling (требуют ранней инвестиции), X Mult (`×1.10–×1.50`, сильны в собранном билде), retrigger/copy, экономические (не увеличивают силу напрямую). Глобальные `×2` — только редкие risk/reward карты; порядок применения фиксирован; босс может отключать отдельный тип множителя.

> **Жёсткое ограничение реализации.** Исход серии считается ELO по основанию 10 с делителем `22`, откалиброванным под шкалу `76–99`. Если Tournament Power инфлирует до ~180 при неизменном делителе, вероятность победы в каждом матче уходит в 1 и турнир перестаёт быть турниром. Либо Tournament Power остаётся в диапазоне порядка `60–110` (тогда множители малы), либо делитель масштабируется вместе со шкалой. Это часть DoD `R7.1`/`R8.2`, а не деталь калибровки.

##### Экономика и цены

- **Базовая цена не зависит от номера этапа.** Один и тот же товар того же качества стоит одинаково на Stage 2 и Stage 22. Этап влияет на вероятность качества, доступный контент, доход, boss pressure и market modifiers — но не входит в базовую формулу цены. Цену меняют только явные модификаторы: качество, Tactic/Item, скидка, Voucher, Stake, событие, trade-in. **Дороже за то, что герой удачно усиливает состав, не делаем** — это наказание за найденную синергию.
- **Цена героя зависит от качества.** Стартовая шкала: `common 4 / unique 7 / mythic 12 / immortal 20`. Числа — placeholder под симуляцию, но инвариант жёсткий: `common < unique < mythic < immortal` **и** `price(тир) = price(common) + Σ upgradeCost(common→тир)` — купить готовый тир стоит ровно столько же, сколько вырастить его из common (`4+3=7`, `7+5=12`, `12+8=20`). Оба пути к immortal равноценны; ломать это калибровкой молча нельзя.
- **Reroll рынка дорожает внутри Буткемпа** (`base + число рероллов в этом Camp`: `2 → 3 → 4 → 5…`) и сбрасывается в следующем. Ограничивает принудительный поиск идеальной карты.
- **Доход не должен обесценивать рынок.** Линейно растущая выплата при статичных ценах быстро делает покупки бесплатными. Переходим к: умеренной базовой выплате по типу этапа + бонусу за overperformance + interest за накопление + экономическим пассивкам + дорогим late-game sinks.
- **Пара Small/Large Gold — доминируемый выбор и убрана.** Схема: призовые начисляются автоматически → игрок выбирает одну из **содержательно разных** наград → открывается Market. Реализованный набор (2026-07-27) — три вида пользы: деньги, билд-карта (Tactic/Camp Action) и утилита-токен (бесплатные реролы рынка либо бесплатное улучшение качества героя). Инвариант: виды в наборе не повторяются, поэтому «строго лучше» структурно невозможно. Booster packs, Form Upgrade offer и trade-in coupon остаются за будущими системами.
- **Проценты за накопление реализованы:** `+1 золото за каждые N на руках, не больше cap`, начисляются вместе с призовыми и считаются с баланса, донесённого до Буткемпа. В Cheat Mode не начисляются. Выплата показывается разложенной на призовые и проценты — иначе решение «потратить сейчас против накопить» невидимо.
- **Поздние синки реализованы (2026-07-29, `T5.9`).** Три расходуемые покупки Буткемпа с геометрически растущей ценой: **усиленные сборы** (`+1 Base` на один следующий этап), **смена правила этапа** (другое правило босса вместо текущего) и **разведка за золото**. Три правила, которые за ними стоят:
  - **Расходуемые, а не постоянные.** Синк конвертирует золото в прохождение этапа, а не в постоянный прирост: иначе поздние деньги обгоняли бы ускоряющуюся угрозу и Династия перестала бы кончаться, что противоречит §5.9.2.
  - **Цена геометрическая** (`base · 2ⁿ` внутри лагеря). Доход растёт линейно по этапу, угроза акта — квадратично; линейный по цене синк либо не поглощает накопленное, либо становится бесконечным `+OVR`. При геометрии 900 золота покупают пять подготовок (`20+40+80+160+320`), а не сорок пять.
  - **Курс намеренно плохой** (20 золота за `+1` на этап против ~8 за `+2..3` навсегда с рынка). Синк — последнее средство для лагеря, где купить больше нечего, а не источник силы; инвариант закреплён тестом.
  - **Booster packs отброшены замером,** а не мнением: в насыщенном лагере лучшая карта рынка даёт +0.04 Team OVR, поэтому добавлять карты в такой пул — удлинять клик «дальше».

##### Формы игроков: тот же человек в лучшей форме

**Баг (подтверждён).** `marketPlayerCandidates` сворачивает все snapshot'ы игрока до самого сильного (`bestByPlayer`) и полностью исключает любой `accountId` из `usedPlayers`. Отсюда сразу две проблемы: выбранного игрока нельзя позднее улучшить до более сильной турнирной формы, а для ещё не выбранного рынок сразу показывает его максимум вместо честной рулетки форм.

Модель: **жёсткой привязки тиров формы к актам нет.** Игрок уровня 90–99 может встретиться уже в первом Буткемпе — это редкое, дорогое и определяющее направление забега событие (перенос принципа Balatro «редкая сильная карта может выпасть рано»). Этап влияет на **odds**, а не на eligibility; тиры определяются percentile внутри роли и формата, а не одним универсальным порогом OVR.

Разделяются понятия **личности** и **формы**: один `accountId` не может занимать два активных слота (это уже гарантирует `assertPlayerReplacement`), но другой snapshot той же личности может прийти как `Form Upgrade` или sidegrade. Chemistry строится на `accountId` и переносится сама; team/event-зависимые параметры обновляются; **manual-назначение героя при апгрейде той же личности сохраняется** (сейчас сбросилось бы). Цена формы зависит от её внутренней силы, а не от этапа; для апгрейда той же личности применяется trade-in, чтобы не платить полную цену второй раз. Карточка объясняет происхождение формы — команда, событие, год — а не только итоговый OVR.

**Нижняя граница рынка.** Рынок не выставляет формы ниже строгого из двух порогов: кривой по этапу и «явно хуже того, что уже стоит в этой роли». Причина — замер: при чисто перцентильных тирах на последнем этапе четверть карт оказывалась в диапазоне 56–74 OVR против состава 85+. Это не ловушка, а шум: ловушка обязана быть соблазнительной и неправильной, а карта, которая слабее всей пятёрки на два десятка очков, никого не соблазняет — она лишь съедает дорожающий reroll. Формы чуть слабее активных остаются и остаются ловушками. Отдельно: **форма своего игрока предлагается только как строгий апгрейд** — у неё меняется только Base (Chemistry и Hero Synergy привязаны к `accountId` и переносятся), поэтому не-апгрейд доказуемо мёртв.

Ранний игрок 95 не убивает прогрессию: он закрывает один слот из пяти и один слой силы, а Chemistry, Hero Synergy, качество героев, Tactics/Items, множители, экономика, подготовка к боссу, резерв и Stakes остаются. Рынок не должен сводиться к поиску пяти максимальных OVR.

##### Разделение флагов редкости

**Баг (подтверждён).** Один `rarityEnabled` одновременно глушит случайные дропы, отображение качества **и ручное улучшение** — поэтому в первом забеге Common-героя нельзя прокачать в Буткемпе, хотя это и было продуктовым намерением. Вводятся независимые `rarityDropsEnabled` / `rarityUpgradesEnabled` (+ производный `rarityUiVisible`):

| Сценарий | Дропы | Ручное улучшение | UI качества |
|---|---:|---:|---:|
| Первый Roguelite Run | ❌ | ✅ | В Буткемпе — да |
| Последующие Roguelite Runs | ✅ | ✅ | Да |
| Quick Draft | — | — | Нет |

Миграция сейвов не нужна: `SavedRun.balanceConfigVersion` уже инвалидирует несовместимый roguelite-resume, а разделение флагов бампает версию по контракту `game/balance.ts`; legacy `rarityEnabled` читается как fallback для обоих новых флагов.

##### Полный пропуск турнира

Две **разные** функции: существующий `Skip phase` перематывает текущий визуальный reveal (группы либо плей-офф), новый **`Show result`** мгновенно доводит турнир до финального snapshot. Кнопка живёт в самой нижней панели действий турнира рядом с индикатором Live, а не прячется в Settings: решение «смотреть или пропустить» принимается ситуативно. На мобильном/TMA кнопки складываются вертикально и не перекрывают Telegram safe area.

Это **presentation shortcut**, доступный и в Classic, и в Roguelite: результат весь считается в конструкторе `TournamentEngine`, поэтому `Show result` не пересчитывает исход, не трогает seed и не может разойтись с просмотренным вручную турниром. Настройка по умолчанию (`Full / Fast / Results only`) — поздняя необязательная задача; автоматический `Results only` без явного согласия не включаем.

##### Cheat Mode

Правило **конкретного забега**, а не глобальная настройка: выбирается до старта в отдельной секции `Special rules` экрана конфигурации Roguelite Run, по умолчанию `false`, после старта не меняется, взаимоисключающ с Hard Mode. Переход `Off → On` требует подтверждения в модалке (RU/EN), честно предупреждающей, что забег быстро потеряет смысл и не попадёт в обычную статистику.

Бесконечное золото реализуется **булевым флагом**, а не числом `Infinity` (оно не переживает JSON). Cheat Mode обходит **только** проверку и списание золота; `freeMarketRerolls`/`freePlayerSwaps`/слоты/interest ведут себя как обычно; операции по-прежнему валидируют payload и слоты. UI показывает `∞` вместо числа и постоянный бейдж `CHEAT MODE · ∞ GOLD`.

Cheat-забег не открывает Stakes и достижения, не идёт в обычный win-rate, лидерборд и дейлик, может сохраняться/resume и шериться только с явной пометкой. **Отдельно важно:** мета-гейт редкости считает записи карьеры в режиме `run`, поэтому cheat-запись обязана исключаться и из агрегатов, и из этого счётчика — иначе читерский забег откроет редкость следующему честному.

##### Прочие подтверждённые дефекты

- **Last Dance удаляет именно саппортов.** Пак строится в порядке `Safelane → Mid → Offlane → Support → Support`, а сужение делает `splice` по хвосту — это не случайное уменьшение рынка, а систематическое удаление обоих support-офферов. Тактика обязана уменьшать **количество** вариантов, а не запрещать роль: сбалансированная выборка с гарантией минимум одного core и одного support, детерминированная по seed.
- **Scouting дублирует уже видимое.** Правило босса и так показано заранее; разведка должна раскрывать *дополнительную* информацию, а не повторять её.

##### Dota-слой билда (после контрактов, не раньше)

- **Hero tags курируются вручную** и версионируются: `web/src/data/heroTags.v1.json`, три слоя — объективные (attribute, melee/ranged), lore (dark/light/demon/undead/spirit/dragon/celestial/void/nature/beast/mechanical) и gameplay (summon/illusion/control/global/save/heal/push/burst/mobility/stealth/scaling/teamfight/pickoff). Динамический вывод тегов из патча/матчей запрещён: обновление данных сломало бы старые seed. Отдельный `heroTagsVersion` **не заводим** — определения входят в `BALANCE_CONFIG_VERSION`, которая уже сидит в `RunLink`/`SavedRun`.
- **Пассивки на основе Dota-предметов** — первый production-набор ~25–35 качественно связанных предметов (build-defining, economy, boss protection, scaling, copy/retrigger, risk/reward, scouting, hero-tag synergy), а не весь список предметов с поверхностными `+N`.
- **Арт карточек не блокирует механику:** в данных сразу предусмотрен `artKey`, до готовности ассетов UI использует единый placeholder. Лицензионные ограничения на оригинальные Dota-иконки проверяются отдельно; без подтверждения используем собственные стилизованные иллюстрации.

Массовую реализацию предметов **не начинаем** до готовности трёх вещей: контракт Tournament Power, схема hero tags и полноценный full-run симулятор.

##### Что должен уметь balance simulator до фиксации чисел

Симулятор обязан играть **легальный полный забег** с учётом качеств героев, ручного улучшения, Tactics/Items, Camp Actions, форм игроков, резерва, дорожающего reroll, interest, boss conditions, Tournament Power, 25 этапов, Династии и Stakes (Cheat Mode — отдельный исключённый профиль). Минимум стратегий: random, greedy Team OVR, greedy Tournament Power, economy-first, synergy/build-aware, static roster control, oracle upper bound. Метрики по каждому этапу: survival rate, распределение мест, `p50/p90/p99` по Team OVR / Tournament Power / золоту, число покупок и реролов, средние качества, число активных пассивок, доля забегов с ранней Peak-формой, причины поражения. В отличие от Balatro исход турнира несёт дисперсию сетки и симуляции, поэтому баланс нельзя строить только по среднему Team OVR: нужны измеренные вероятности топ-8 / топ-4 / топ-1 при заданной разнице силы.

##### Версионирование

Run-only изменения баланса → bump `BALANCE_CONFIG_VERSION` **в задаче реализации**, а не при правке текста. Изменение структуры сейва → миграция либо новая save-версия. `ratingModelVersion` бампается **только** при изменении рейтинговой модели игроков — ни одно решение этого раздела её не трогает.

#### 5.9.4. Game feel — обратная связь как продуктовое требование (аудит 2026-08-09)

Источник: [аудит feel-слоя](audits/2026-08-09-roguelite-feel-audit.md); декомпозиция — BACKLOG **R15**.
У Balatro juice — не украшение поверх механики, а половина продукта. Механическое Balatro-парити
(§5.9.3) закрыто, но три самых громких момента цикла остаются немыми: покупка, «этап пройден»,
reveal турнира. Требования:

- **Каждое значимое событие забега получает соразмерный отклик.** Лестница эскалации: обычное
  действие — 1–2 слоя (exit-анимация, вспышка); редкое (босс, апгрейд редкости) — плюс пульс/синг;
  кульминация (этап пройден, Aegis, смерть забега) — полная секвенция. Одинаковый отклик на всё
  равен отсутствию отклика.
- **Числа решений не анимируются набеганием.** Золото и Run power показываются точными (урок R14.4:
  rAF-набег врёт в фоновой вкладке); анимируется вспышка/появление, не значение.
- **Motion-правила** — [design-language.md](design-language.md): бюджет входа 0.3–0.5s, стаггер по
  плотности, вспышка-не-состояние, глобальные keyframes, проверка `getAnimations()`,
  `prefers-reduced-motion` обязателен. Shake — только на кульминациях и с тумблером в Settings.
- **Звук — отдельный слой** (R15.5): WebAudio с unlock по первому жесту, master-тумблер, маленький
  семантичный набор SFX с эскалацией питчем/слоями. Звук не является условием играбельности —
  режим полноценен и в тишине.
- **Изоляция Classic сохраняется:** весь feel-слой — презентация; `Rng`-поток, golden-фикстуры и
  `BALANCE_CONFIG_VERSION` не двигаются.

### 5.10. Build-системы и мета-прогрессия 🆕
Применяем принципы Balatro, но переводим их на язык Dota:

- **Tactics** — ограниченный набор пассивных модификаторов забега с условиями (`+` за общий регион/эру, широкий hero pool, сыгранные пары, comeback-состав и т.п.). Это источник разных билдов; конкретные эффекты требуют отдельного balance spec.
- **Camp actions** — одноразовые действия между этапами: scrim, bootcamp, scouting, hero practice, stand-in/transfer. Они меняют решение сейчас, а не дают вечный бонус аккаунту.
- **Boss conditions** — ограничения вроде урезанного hero pool, штрафа несбалансированному ростеру, давления конкретной меты или запрета одного типа синергии. Условие показывается заранее, чтобы игрок мог адаптироваться.
  - **Порог условия не бывает абсолютной константой** (решение 2026-07-30, `R12.5`). Величины, которые судят боссы, монотонно растут по ходу забега, поэтому константа пересекается ровно один раз и делит сезон на «штраф всегда» и «штрафа никогда»: решением она не является нигде. Порог обязан либо расти вместе со своей величиной (рампа по актам, продолжающаяся в Династии), либо не зависеть от величины вовсе — считать СТРУКТУРУ состава (сколько героев вне репертуара, сколько забанено), а не очки. Второе предпочтительнее там, где величина упирается в потолок: планку по такой величине выполняют все по определению.
- **Economy** — валюта за прохождение и overperformance; выбор между немедленным усилением и накоплением. Реролл рынка и реролл draft-пака — разные расходы.
- **Meta progression** — открывает новые tactics, форматы, stakes и challenge-наборы. Постоянные `+OVR` не выдаём: они размывают честность seed/challenge.
- **Replayability** — seeded run, daily challenge, escalating stakes, статистика открытий и история забегов.

#### 5.10.1. Штаб, Playbook и Буткемп — разные уровни

| Уровень | Когда доступен | Что в нём живёт |
|---|---|---|
| **Штаб** | Между забегами | Коллекция открытых Tactics/Camp Actions, Playbook, Stakes, статистика и трофеи. Это мета-хаб, а не источник постоянных статов. |
| **Playbook** | Выбирается перед забегом | Небольшой набор открытых карточек, которые могут встретиться в наградах и Market. Карточки из Playbook **не активны бесплатно со старта**. |
| **Буткемп / Camp** | Между этапами текущего забега | Reward, Market, перестройка ростера и hero pool, экипировка Tactics, применение Camp Actions и подготовка к следующему условию. |
| **Тактическая панель** | Внутри текущего забега | До **5 пассивных Tactics/Items** в общем инвентаре и до **2 одноразовых Camp Actions**. Эффекты и содержимое сбрасываются после Win/Loss. |

Так мы не заводим рядом с Tactics ещё один абстрактный «инвентарь»: карточки — интерфейс уже зафиксированных build-систем. Термин **Штаб** оставляем постоянному пространству между забегами, **Буткемп** — остановке внутри забега.

> ✅ **Решено 2026-08-02 (повторный плейтест, BACKLOG PF-2):** общий пассивный инвентарь расширен с 3 до **5** слотов, Camp Actions остаются в 2 слотах. Цель — дать место связке нескольких условных карт, а не заставлять билд замерзать после первых трёх находок. Изменение входит в `balanceConfigVersion`; коэффициенты и потолок силы подлежат следующему прогону T6.3/R10.

#### 5.10.2. Жизненный цикл карточек

1. После пройденного этапа игрок получает Reward: выбор одной из трёх карточек либо экономической награды.
2. В Буткемпе карточку можно экипировать, заменить ею занятую, оставить в ограниченном запасе или конвертировать по правилам экономики. Market может продавать карточки, Camp Actions и улучшения ростера/hero pool.
3. **Tactics/Items** работают пассивно и делят 5 общих слотов. **Camp Actions** занимают 2 слота и разыгрываются между этапами; активных кликов во время симуляции турнира не вводим.
4. После Win/Loss вся сила текущего билда исчезает. За milestones открываются **определения** новых карточек в коллекции Штаба, а не усиленные экземпляры и не постоянный `+OVR`.
   - **Editions — вторая ось карточек (R13.5, реализовано 2026-08-09).** Качество — конечная шкала величины; Edition меняет ПОВЕДЕНИЕ. Первая — `Charged`: карточная награда актов 3+ может прийти «заряженной» (отдельный Rng-поток, потоки наград не двигаются; только тактики и предметы с силовым эффектом). Заряд +1 за пройденный этап с выполненным условием (потолок 3), каждый даёт +20% к эффекту карты; поломка условия сжигает заряды; drawback не масштабируется. Визуальные оси разведены: качество владеет цветом рамки, Edition — бейджем (`--edition-charged`). Числа — placeholder до A/B-калибровки по протоколу R10. Остальные Editions (`Crystal` и др.) — только после замера `Charged` симулятором.
5. Playbook вводится только после проверки базовой петли и баланса. Стартовая гипотеза — около 8 выбранных карточек: он ограничивает будущий reward/market pool, но не даёт стартовых бонусов. Для daily/challenge используется фиксированный Playbook; обычный seeded run включает `playbookId` и `balanceConfigVersion` в воспроизводимое состояние.

#### 5.10.3. Первый курируемый набор Tactics

Карточка должна менять оптимальный способ сборки и содержать условие или цену. Безусловные «`+N%` ко всему» не используем. Согласованный стартовый набор-кандидат:

- **Signature Specialists** — первые 30 pro-игр игрока на назначенном герое дают усиленный вклад в Hero Synergy, но игроки с Base OVR выше 86 получают штраф. Это безопасная версия исходной идеи «бонус от количества игр»: она не умножает без ограничений уже games-driven Hero Synergy.
- **Old Teammates** — Chemistry пар с 50+ совместными pro-играми усиливается, но замена игрока в Market стоит дороже.
- **Fresh Project** — после каждого пройденного этапа самая слабая по Chemistry пара получает временные virtual co-games внутри текущего забега.
- **Wide Pool** — бонус за широкий пул архетипов, но вклад редкости героев становится слабее. *(Реализация 2026-08-30, b1.42.0: +Hero Synergy лестницей, когда назначенные герои закрывают 10+ разных gameplay-тегов словаря heroTags — случайная пятёрка покрывает 8–9, порог требует намеренного драфта; редкость ×0.5, пока карта экипирована. Числа — placeholder до живого плейтеста: сим-агент не драфтит героев намеренно и это условие не отыгрывает.)*
- **No Superstars** — состав без игроков с Base OVR 88+ получает бонус к Chemistry; появление суперзвезды отключает эффект.
- **Last Dance** — исторические игроки одной эпохи усиливают друг друга, но Market показывает меньше вариантов замены.

Точные коэффициенты, caps, порядок применения и определения hero-архетипов входят в отдельный balance spec. Tactics модифицируют понятные входы/слагаемые `Base + Hero Synergy + Chemistry`; UI обязан показывать источник каждого изменения.

#### 5.10.4. Поддерживающие системы

- **Резервный состав.** Внутри забега сохраняются все снятые игроки и малый резерв hero pool (до трёх героев). Подготовка к boss condition становится перестановкой состава с потерей/сохранением Chemistry и Hero Synergy, а не мгновенной покупкой числа.
- **Предпросмотр следующего условия.** До покупок игрок видит следующий boss condition либо достаёт информацию через Scouting. Все обязательные контр-условия должны быть заранее адаптируемыми, а не угадываться постфактум.
  > ✅ **Уточнено 2026-07-29 (`R9.4`).** Правило ПРЕДСТОЯЩЕГО этапа видно всегда и бесплатно — иначе «заранее адаптируемо» не выполняется. Scouting раскрывает то, чего ещё не видно: правило **следующего боссового турнира** (на несколько этапов вперёд) с оценкой против текущего ростера. Раскрытое знание не исчезает в следующем Буткемпе — оно держится до самого турнира, а счётчик «через N этапов» уменьшается.
- **Прозрачный breakdown.** Любая награда, покупка, перестановка или карточка показывает `до → после`, изменённое слагаемое Team OVR, сработавшее условие и итоговый эффект будущего boss condition.
  > ✅ **Уточнено 2026-07-30 (`R13.3`, по итогам плейтеста).** Требование — про ДОСТУПНОСТЬ разбора до покупки, а не про его одновременное присутствие на экране. Когда весь разбор печатается на самой карточке, она растягивается под объём текста, карточки перестают быть сравнимыми между собой, а экран читается как debug-панель. Поэтому информация живёт на двух уровнях: **карточка отвечает на «брать или нет»** (что это, цена, одна главная дельта, риск, короткое условие) и имеет ФИКСИРОВАННЫЙ размер; **инспектор отвечает на «почему»** (полный `до → после` по слагаемым, назначение героев, теги, условие целиком) и открывается по выбору карточки. Нулевые дельты не показываются вовсе: `TEAM OVR 0` — это шум, а не информация.
  > Визуальные оси не должны конкурировать: редкость владеет цветом рамки, поведенческий модификатор карточки — материалом/текстурой, роль — бейджем, дельта — текстом.
  > ✅ **Уточнено 2026-07-31 (плейтест).** Точка входа в разбор — **вся карточка целиком**, а не отдельный элемент внутри неё: игрок выбирает предложение, а не «строку с числом». Разбор открывается **оверлеем поверх сетки** (соседние карточки затемняются) — той же карточкой, только крупнее и со всей информацией. Не раздвигать сетку на месте: раскладка не должна дёргаться, соседи не должны прыгать, и на действие приходится одна короткая анимация вместо перекомпоновки ряда.
  > Отдельно: **уменьшение высоты карточек не заменяет разделения экрана**. Замер плейтеста — ~29 карточек одновременно в одной вертикальной ленте; пока все разделы (награда, рынок, билд, подготовка, резерв) рендерятся сразу, экран остаётся «инвентарём», какой бы компактной ни была отдельная карточка. На экране обязан быть виден один активный раздел.
  > ✅ **Уточнено 2026-08-02 (`R13.4`, плейтест).** `Next stage / Give up` не закрепляются поверх viewport: fixed/sticky-панель перекрывает нижние карточки и конкурирует с сеткой. Действия остаются обычным футером сразу после активного раздела; компактность даёт сама секционная навигация. На карточках замены героя, улучшения редкости и перестановки резерва показывается только итоговая дельта **Run Power** — с повторной оценкой Tactics, редкости и предметных множителей; `Base / Hero Synergy / Chemistry` доступны в связанном оверлее, но не дублируются на карточке.
- **Stakes после первой победы.** Следующие уровни сложности добавляют ограничения, составы boss conditions и экономические trade-off, а не только повышают OVR поля. Постоянного бонуса аккаунту к силе нет.

#### 5.10.5. Порядок внедрения

1. Доделать петлю `Reward → Camp/Market → следующий этап`.
2. Добавить одну мягкую валюту, market reroll и минимум три категории покупок.
3. Добавить 5 общих пассивных слотов Tactics/Items и 2 слота Camp Actions.
4. Выпустить малый курируемый набор карточек с условиями/trade-off и прозрачным breakdown.
5. Добавить заранее видимые boss conditions и адаптацию через резерв/Scouting.
6. Только после симуляции и проверки баланса добавить Штаб, постоянную коллекцию, Playbook и Stakes.

Первая версия полного цикла должна доказать арку на 4 этапах с малым курируемым набором Tactics; крафт, уровни карточек, дубликаты, несколько постоянных валют и постоянные stat-upgrades не вводим до телеметрии и симуляции баланса.

### 5.11. Telegram: бот + Mini App 🆕

Второй канал доставки той же игры. Веб остаётся основным, TMA — не форк, а **та же сборка `web/`**, открытая внутри Telegram; бот вокруг неё отвечает за вход и служебную информацию.

**Зачем.** Дистрибуция (ссылка в чат вместо «зайди на сайт»), мобильный сценарий без установки, и площадка под будущие соц-фичи из §5.9 (дейлик, лидерборд) — они по природе про «поделиться результатом», а Telegram это делает лучше сайта.

**Что делает бот.** Две группы команд:
- **Служебные** — то, ради чего бот заводится в первую очередь: жив ли сайт, свежи ли данные, какие версии схемы и модели рейтинга. Это те же поля `manifest`, что показывает страница настроек; data-refresh идёт кроном, и «данные протухли» — реальный отказ, который иначе замечаешь глазами.
- **Справочные** — короткие выжимки из датасета: топ героев, карточка героя, профиль игрока, его тиммейты. Пересобирают на сервере то же, что считает клиент на страницах справочника.

**Отношение к хардкору.** Блокировка справочника (`isCodexLocked`) — свойство **клиента во время забега**. Бот — отдельная поверхность и о забеге не знает, поэтому запретить там просмотр героев игрока технически можно только зеркалированием состояния через сервер. Считаем это приемлемым: хардкор — договор с собой, а не античит; кто хочет обойти, откроет браузер. Решение осознанное, а не упущение.

**Границы.**
- TMA **не** получает отдельный фронт: любая правка UI живёт в `web/` и приезжает в оба канала. Расхождение допускается только там, где Telegram диктует своё (кнопка «назад», safe-area, закрытие приложения).
- Бот **не** становится вторым бэкендом: он ходит в тот же Go API и ту же статику, что и веб.
- Сохранения остаются local-first (§6.2). В webview Telegram `localStorage` живёт по своим правилам и может очищаться, поэтому для TMA важнее облачные сейвы (T8.4) либо `WebApp.CloudStorage` — наш сейв это config+seed+лог действий, он компактный и в лимиты CloudStorage укладывается.

### 5.12. Arena — онлайн-турнир на 18 команд (WebSocket) 🆕

Запрос 2026-08-09, форма уточнена пользователем 2026-08-10: НЕ дуэль, а **общий турнир-лобби**.
Комната до **18 человек** (число команд классического турнира), каждый человек — команда; недобор
заполняют боты. Все драфтят из **одного общего пула** игроков и героев, затем играется один турнир
(группы + плей-офф) той же вероятностной моделью на общем сиде — **победителя определяет то, что
он надрафтил**. Отдельной дуэли/очной серии нет (решение 2026-08-10): комната на двоих — это тот
же турнир с 16 ботами. Декомпозиция — BACKLOG **M10**; реализация не начата, это продуктовая рамка.

**Драфт — одновременные раунды с приоритетом змейки (решение 2026-08-10).** Ключевая проблема
формата — честность («один забрал всех сильных») и темп (последовательная змейка на 180 пиков —
это 30–45 минут ожидания чужих ходов). Решение закрывает обе:

- Приоритет посадки роллится по сиду комнаты и виден заранее; каждый раунд змейка инвертируется
  (1→18, затем 18→1, …) — проигравший приоритет поднимается в следующем раунде.
- Раунд ~25с: **все команды выбирают одновременно** по одному пику (+ необязательный запасной).
  По истечении сервер резолвит раунд атомарно: конфликт за одного игрока/героя выигрывает лучший
  приоритет раунда, проигравшему достаётся запасной или авто-пик. За раунд каждый получает ровно
  один пик — «скупить всех» невозможно по построению. Весь драфт ~8–10 минут.
- **5 раундов игроков** (пик занимает свободный ролевой слот команды: safelane/mid/offlane/
  support×2; роль игрока — из данных), затем **5 раундов героев**.
- Игроки и герои **уникальны глобально** (решение 2026-08-10): взятое исчезает из пула у всех
  (~90 из ~120 игроков и 90 из 127 героев разбираются — дефицит и есть соль драфта).
- Герой при пике автоназначается лучшему слоту своей команды (тот же assignment/bestHeroOption,
  что в игре); до лока пики героев можно свапнуть внутри своей команды.
- Таймаут хода и дисконнект: авто-пик бот-политикой — комната никогда не ждёт одного человека.

**Боты.** Пустые слоты лобби и отвалившихся ведёт политика агентов балансового симулятора
(`synergy-build` как сильный бот, ослабленные варианты для разброса) — драфт по OVR/синергии уже
написан и откалиброван в `scripts/sim_run.ts`, политика портируется, не изобретается.

**После драфта.** Лок → общий сид → турнир 18 команд той же моделью (`TournamentEngine`); reveal
все смотрят синхронно — симуляция детерминирована, сервер раздаёт только seed и составы.
Career-запись видом `arena` (не смешивается с одиночными агрегатами); серверный лидерборд — за
M9/T8.5.

**UI.** Четвёртая карточка режима на главной; акцент режима — **красный в нашей гамме** (решение
2026-08-10): token-набор `data-accent="arena"` в `design/tokens.css` для обеих тем, никаких
хардкодов. Экран драфта — в стиле Dota ban/pick (референс-скрин 2026-08-10): пул по центру
(игроки — колонками по ролям, герои — сеткой по атрибутам), таймлайн 18 команд по бокам с
заполняющимися пиками, таймер раунда сверху, лента «предыдущие пики». Всё из `ui/`-примитивов.

**Сервер — авторитет фаз и резолва раунда.** Фазы `lobby → draft(rounds) → lock → tournament →
done`; на сервере живут пул, приоритеты, атомарный резолв раунда и валидация пика («слот роли
свободен», «есть в пуле») — Go-подмножество правил драфта; полный счёт по-прежнему клиентский и
не форкается. Комната **пинит версии** `manifest` и `BALANCE_CONFIG_VERSION` при джойне — клиент
с другим датасетом получает «обнови», иначе пулы рассинхронизируются. Reconnect по токену комнаты.

**Дорожка** (каждый шаг играбелен):
1. **MP0** — ws-транспорт + комната по коду + presence (Fly, TMA-webview, reconnect).
2. **MP1** — комната → ready → турнир на общем сиде: драфт пока из ЛИЧНЫХ паков (существующий
   `DraftScreen`, тайно и параллельно), боты добирают, общий reveal. Играбельный мультиплеер
   почти без новых правил.
3. **MP2** — целевая форма: общий пул + одновременные раунды с приоритетом змейки + экран драфта
   в стиле Dota + свап героев до лока.
4. **MP3** — баны (1 бан героя на команду перед драфтом, как в референсе), рейтинг/лидерборд,
   матчмейкинг, спектаторы; анти-чит серверной ре-симуляцией (deps T8.5/T8.6).

**Границы.** Игровые данные остаются статикой (ws не раздаёт JSON сцены); `scoreTeam` и
`ratingModelVersion` не форкаются; протокол версионируется с первого сообщения; комнатная логика —
`server/internal/service`, transport только upgrade/кодек (ADR 0002). Roguelite-петля в Arena не
тянется: режим строится на Quick Draft как на кирпиче (тот же принцип, что §5.9.2).

**Связность — часть режима, а не отдельная забота (решение 2026-08-14, [ADR 0003](adr/0003-offline-first-pwa.md)).**
Arena — единственный режим, которому интернет нужен по смыслу, поэтому она обязана говорить об этом
честно, а не молчать мёртвым кликом. Различаем два случая:
- **Вход в офлайне.** Карточка режима несёт признак «нужен интернет» и в офлайне недоступна с
  внятной причиной; на входе — активная проверка (`navigator.onLine === false` ⇒ точно офлайн и в
  сеть не ходим; `true` ничего не гарантирует — в самолётном Wi-Fi он тоже `true`, поэтому
  положительный ответ даёт только пробник к `/healthz`). Провал — экран «нет соединения» с
  повтором, а не бесконечный спиннер. Задача — BACKLOG `T11.3`.
- **Обрыв связи внутри лобби/драфта.** Это НЕ тот же случай: раунды идут по таймеру, и молчащий
  клиент нельзя отличить от думающего. Реконнект по токену комнаты, поведение при таймауте
  (бот-политика доигрывает пик) и порог отчисления из комнаты проектируются **вместе с
  ws-протоколом в MP0**, а не допиливаются после. Офлайн-Arena с локальными ботами под видом
  онлайна не делаем — это подмена сути режима.
- **MP1 сыгран (2026-08-26): турнир комнаты на общем сиде, драфт из личных паков.** Транспорт —
  relay-лог Дуэли (§5.13) без единой правки сервера: host шлёт start, каждый драфтит свои паки
  обычным DraftScreen, сдаёт состав, host лочит — несданных и недобор до 18 ведут боты (порт
  жадного sim-агента), и каждый клиент детерминированно строит ОДИН турнир (canonical-рассадка
  по силе + эпсилон против ничьих; подтверждено тестом и живым прогоном двух ws-клиентов —
  таблицы идентичны до знака). Общий пул и одновременные раунды — по-прежнему MP2; анти-чит
  (teamOvr принимается на веру, refs+heroes уже в логе) — MP3.
- **MP2 сыгран (2026-08-28): целевая форма — общий пул + одновременные раунды.** Драфт из
  ЛИЧНЫХ паков (MP1) заменён общим: 5 раундов игроков + 5 героев, пик + необязательный запасной,
  приоритет змейки по сиду комнаты, конфликт выигрывает лучший приоритет раунда, взятое исчезает
  у всех; несданных и недобор ведёт бот-политика. Резолв раунда — не Go-сервер, а та же
  детерминированная применялка relay-лога (сервер снова не менялся): раунд резолвится в точке
  лога, где сдал последний человек, либо по close хоста — его шлёт таймер хоста (~30с), как
  «host лочит» в MP1; серверный авторитет фаз и валидация пика откладываются к анти-читу MP3.
  Свап героев до лока опущен: назначение авто (Hungarian) и так оптимально — свап был бы мёртвым
  действием. Побочно закрыт дефект MP1: reload больше не теряет драфт (reconnect реплеит лог,
  включая свою заявку), а teamOvr больше не принимается на веру — каждый клиент считает все 18
  команд сам. Живой прод — за T9.0.

### 5.13. Дуэль — онлайн 1×1 капитанским драфтом (M-DUEL, решение пользователя 2026-08-26) 🆕

Пятый режим. Отмена дуэли 2026-08-10 касалась дуэли КАК ЗАМЕНЫ Arena — теперь она возвращена
**отдельным** режимом рядом с ней (Arena остаётся турниром на 18): два капитана с разных устройств
входят в комнату по коду, **змейкой собирают пятёрки из общего пула** (mixed-паки; личность, ушедшая
к одному, второму не предлагается), затем **на каждую игру серии bo1/bo3/bo5 играют капитанский
драфт героев**: пул = объединение репертуаров всех десяти игроков (top-героев по pro-играм — баны
бьют по comfort-зоне соперника), баны чередуются, пики змейкой, приоритет первой стороны чередуется
по играм. Игра решается той же ELO-кривой, что все турниры (`eloWinProbability`, делитель
масштабируется от средней силы игры), сила пятёрки — тем же `scoreTeam`.

Архитектура: **полный реюз relay-инфраструктуры MP0** — комната/код/версии/reconnect общие с
Arena; сервер получил универсальный `relay` с упорядоченным логом (`{seq, from, payload}`, сервер —
источник порядка и отправителя, полезную нагрузку не понимает; лог в памяти комнаты, реплей на
входе/reconnect). Протокол дуэли — детерминированная применялка лога на клиентах
(`game/duelProtocol`): оба применяют один лог одними правилами ⇒ одно состояние без сверки; свои
действия не применяются оптимистично — только с возвратом от сервера. Невалидное сообщение (чужой
ход, зритель, мусор) молча игнорируется одинаково у всех; рейтинги/карьеру дуэль не пишет —
анти-чит ре-симуляцией не требуется. Обрыв: reconnect-токен + полный реплей лога. Живой прогон —
как у Arena, за деплоем T9.0 (Fly): до него карточка честно гейтится сетью/конфигом API.

**Таймер хода и реванш (2026-08-28).** Ход ограничен ~45с: отсчёт видят оба, по истечении клиент
самого актора шлёт авто-ход (лучший OVR / верх хиро-пула) — комната не ждёт задумавшегося;
отключённого актора таймер не доигрывает (это кейс обрыва, его закрывает reconnect). После
доигранной серии любой капитан запускает реванш той же комнатой: новый сид, те же правила,
стороны меняются (первый пик уходит сопернику) — применялка принимает start поверх завершённой
партии и только от её капитана.

- Быстрый первый рендер (данные статикой, ленивая подгрузка по формату).
- **Детерминизм по сиду** (для дейликов/шеринга).
- Пайплайн повторяем, версионирован, пересобирается одной командой.
- **Собственная айдентика:** пользовательское название и header — **Aegis Draft**. «322-0» допустимо только в документации, credits/описании источника вдохновения и parity-аудитах, но не как логотип или название нашей игры.
- **Не pixel-copy:** из 322-0 заимствуем проверенные UX-принципы и структуру решений, а не его логотип, композицию, палитру или визуальные ассеты. Визуальная система Aegis Draft должна иметь собственные tokens, типографику и характер.
- **Локализация:** интерфейс поддерживает RU/EN; в одном выбранном locale нет смеси языков. Переключение доступно из общего shell, выбор сохраняется, `<html lang>` синхронизируется, неизвестный ключ имеет контролируемый fallback.
- **Темы:** `system/light/dark`; первый визит уважает `prefers-color-scheme`, ручной выбор сохраняется. Все экраны используют семантические color tokens и сохраняют читаемый контраст.
- **Офлайн-доступность** (требование с 2026-08-14, [ADR 0003](adr/0003-offline-first-pwa.md)). После первого захода **все одиночные режимы играются полностью без сети** — включая портреты героев и логотипы команд. Датасет прекэшируется автоматически (не по кнопке: кнопка бесполезна тому, кто уже в самолёте) и обновляется **только целиком и атомарно** — смешать старый `packs.json` с новым `players.json` значит рассинхронизировать `accountId`, а смена `manifest.dataHash` инвалидирует незавершённый забег, поэтому переключение датасета не происходит во время активного забега. Обновление приложения не выполняется самовольно посреди драфта. Интернет обязателен ровно там, где он нужен по смыслу (Arena — §5.12; облачные сейвы/лидерборд/дейлик — ADR 0002), и его отсутствие показывается честным состоянием экрана; серверные записи в офлайне ставятся в очередь и синкаются при реконнекте.

## 7. Технологический стек

### 7.1. Go — data-пайплайн (ядро ценности) + опц. API
ETL: тянуть OpenDota/Liquipedia (goroutines + worker pool + rate-limit), агрегировать матчи, считать рейтинги, генерить `*.json`. Прозрачно и тестируемо заменяет «странный парсинг» оригинала.

### 7.2. TypeScript — фронт + игровая логика
React + Vite + TS. State — Zustand. Пентагон — SVG/Canvas. Логика счёта на клиенте (как в оригинале) — быстро, без сервера.

### 7.3. Runtime: static-first сейчас, Go API позже — обоснование
Твой вопрос: «если для масштабирования лучше Go API — то его». Честный ответ: **для масштабирования сам static-first лучше и дешевле** — JSON на CDN масштабируется практически бесконечно и почти бесплатно, игровая логика на клиенте. Go API нужен **не для масштаба, а для фич с общим состоянием**: глобальный лидерборд, дейлик-сид с валидацией, сохранение забегов, анти-чит.

**Решение:**
- **Сейчас (static-first):** фронт грузит статические JSON; Go = только пайплайн.
- **Фаза 2 (Go API):** добавляем сервис (`chi`/`Fiber` + Postgres/SQLite) под лидерборд/дейлик/сейвы.
- **Заложить сразу:** доступ к данным за интерфейсом (`DataSource`), чтобы подменить статику на API без переписывания фронта.

**Следствие 2026-08-14 — статика доезжает до устройства ([ADR 0003](adr/0003-offline-first-pwa.md)).** Static-first сам по себе не даёт офлайна: CDN всё равно требует сети в момент запроса. Поэтому поверх него — service worker (precache оболочки + датасета, атомарный своп по `dataHash`) и **зеркало арта в репозитории** вместо ссылок на чужой Steam CDN. Это не отход от static-first, а его завершение: сервер по-прежнему не нужен для базовой игры — теперь и сеть тоже. Побочно снимается tainted-canvas, из-за которого шеринг-карточка рисуется без портретов.

### 7.4. Клей — единый контракт данных
JSON Schema как источник истины → генерим TS-типы и валидируем оба конца, чтобы Go-пайплайн и TS-фронт не разъехались.

### 7.5. Итоговая раскладка
```
Go   → ETL-пайплайн (raw → рейтинги → game JSON)     [ядро]
Go   → API (фаза 2: дейлик/лидерборд/сейвы)          [опц.]
TS   → React+Vite фронт + игровая логика             [ядро UX]
Схема → JSON Schema контракт данных                   [клей]
```

Модель поля переведена (2026-07-27, `R7.1`) со «сдвиг-и-кламп» на параметризацию по этапу: замер показывал схлопывание 90% поля в одно значение на первом этапе, теперь `sd` живой на всех этапах, а гибель наивной игры на первом этапе упала 27% → 12%. `dynastyStep`, boss severity, инфляция, survival curve и выбор `20/25/30` этапов остаются за balance simulator (T6.3 → `R10`).
- **F. Частично решено 2026-07-22, число слотов пересмотрено 2026-08-02.** Каркас: 5 общих пассивных слотов Tactics/Items + 2 слота Camp Actions; стартовые Tactics — `Signature Specialists / Old Teammates / Fresh Project / Wide Pool / No Superstars / Last Dance`; сила сбрасывается после забега. Точные коэффициенты, caps, размер Playbook и состав Camp Actions — через отдельный balance spec и симуляцию.
- **G. Драфт героев из паков — решено и реализовано 2026-07-12.** Забег состоит из 5 пиков игроков + 5 пиков героев. Каждый экран пака предлагает ровно 5 доступных героев, дубли исключены; назначение auto выполняет exact matching, Manual остаётся отдельной задачей T3.10. Инспекция игрока и games player×hero реализованы по UX-паттерну референса без копирования его визуального языка. См. аудит `docs/audits/2026-07-12-hero-draft-stats-chemistry.md`.
- **I. ✅ Закрыт 2026-07-29 замером (`R6.4`) — цена одной неудачной сетки в конце сезона.** Вопрос стоял так: §5.9.3 требовала чемпионства и на Stage 20, и на Stage 25, а забег из 25 турниров, теряемый на одном неудачном BO5, — классический источник rage-quit. **Ответ: `топ-2` на Stage 20 (чемпионство там становится бонусной наградой), `1-е` остаётся только на Stage 25; защитный ресурс не нужен.** Основание — `npm run sim -- 60 --finales` на общих сидах: проходимость S20 у билд-агента 83.9% → 93.5%, у жадных 48.3% → 62.1%, общий win-rate при этом **не изменился** (30.0% на обеих кривых). Смягчение не сделало сезон легче — оно перенесло точку обрыва из середины в финал, где за поражением уже ничего не теряется. Полный отказ от чемпионства (`4/3/2/2/2`) даёт 36.7%, но лишает сезон кульминации, поэтому отклонён. Mulligan не вводится: коинфлип-стены в середине сезона больше нет, а вводить страховку от финала значит обесценить сам финал.
- **H. Вердикт итога — решено и реализовано 2026-07-12.** После драфта показываем воспроизводимый прогноз против 18-team field, затем тем же полем играем группы → double-elimination playoffs → Grand Final и выдаём фактическое место. Это не декоративный score verdict: preview и турнир используют один `TournamentEngine`. См. аудит `docs/audits/2026-07-12-tournament-cycle-parity.md` и BACKLOG **TREF2/T5.1**.

## 11. Reference-driven development

Референсы используются как исследовательский материал, а не как безусловная спецификация. Любая просьба сравнить реализацию запускает `reference-parity-audit`: живой проход 322-0/другого референса и Aegis Draft, единый сценарий, матрица `parity / intentional-divergence / defect / missing / not-applicable / unknown`, затем синхронизация подтверждённых выводов с PRD и BACKLOG.

Baseline от 2026-07-11: [reference audit](audits/2026-07-11-322-balatro-baseline.md). Источники продуктовых принципов Balatro: [официальный сайт](https://www.playbalatro.com/) и [официальное описание PlayStation](https://www.playstation.com/en-us/games/balatro/).
